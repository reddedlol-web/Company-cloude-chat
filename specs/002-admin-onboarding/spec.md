# Feature Specification: Админ и самостоятельная регистрация сотрудников

**Feature Branch**: `002-admin-onboarding`

**Created**: 2026-06-29

**Status**: Draft

**Depends on**: `001-company-telegram-bot` (базовый бот, RAG, whitelist, rate limits)

**Input**: Администратор (директор/HR) должен уметь приглашать сотрудников по ссылке, при необходимости с паролем, и видеть, кто пользуется ботом — без ручного редактирования `.env` и без отдельной веб-админки.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Приглашение по ссылке (Priority: P1)

Администратор создаёт приглашение в боте. Бот выдаёт ссылку вида `https://t.me/CompanyBot?start=invite_ABC123`. Админ отправляет ссылку в корпоративный чат или лично сотруднику. Сотрудник переходит по ссылке, нажимает «Start» — и получает доступ к боту.

**Why this priority**: Без этого админ вынужден вручную собирать Telegram ID и править конфиг на сервере.

**Independent Test**: Админ создаёт invite → новый пользователь (не в whitelist) переходит по ссылке → задаёт вопрос → получает ответ.

**Acceptance Scenarios**:

1. **Given** админ в `ADMIN_USER_IDS`, **When** он отправляет `/invite create`, **Then** бот возвращает одноразовую (или многоразовую) ссылку-приглашение и краткую инструкцию для рассылки.
2. **Given** сотрудник перешёл по валидной ссылке и нажал Start, **When** токен не истёк и лимит использований не исчерпан, **Then** его Telegram ID добавляется в динамический whitelist и он может задавать вопросы.
3. **Given** сотрудник перешёл по просроченной или отозванной ссылке, **When** он нажимает Start, **Then** бот сообщает, что приглашение недействительно, и предлагает обратиться к администратору.

---

### User Story 2 - Приглашение с паролем (Priority: P1)

Администратор создаёт приглашение с паролем (например, корпоративный код или одноразовый пароль). Сотрудник переходит по ссылке, бот просит ввести пароль, после успешной проверки — доступ открыт.

**Why this priority**: Защита от «утёкшей» ссылки в публичный чат; контроль, что приглашением воспользовался именно сотрудник.

**Independent Test**: Создать invite с паролем → пользователь без пароля получает отказ → с правильным паролем — доступ.

**Acceptance Scenarios**:

1. **Given** админ создал invite с паролем `summer2026`, **When** пользователь переходит по ссылке и вводит неверный пароль, **Then** доступ не выдаётся, остаётся ≤3 попыток за 15 минут.
2. **Given** пользователь ввёл верный пароль, **When** invite ещё действителен, **Then** он регистрируется и получает приветственное сообщение с остатком дневного лимита.
3. **Given** invite с паролем, **When** админ отзывает invite, **Then** даже с верным паролем новые регистрации невозможны (уже зарегистрированные сохраняют доступ).

---

### User Story 3 - Просмотр пользователей (Priority: P2)

Администратор видит список сотрудников, которые пользуются ботом: имя/username, дата регистрации, активность (запросов сегодня / всего), статус (активен / заблокирован).

**Why this priority**: Директору нужна прозрачность — кто подключился, кто реально пользуется.

**Independent Test**: Зарегистрировать 2 пользователей → `/users` показывает обоих с корректными данными.

**Acceptance Scenarios**:

1. **Given** админ, **When** `/users`, **Then** список до 50 последних пользователей с пагинацией (кнопки «далее»).
2. **Given** админ, **When** `/user <telegram_id>`, **Then** детальная карточка: регистрация, invite-код, запросов сегодня, последний запрос.
3. **Given** админ, **When** `/user block <telegram_id>`, **Then** пользователь теряет доступ немедленно; при следующем сообщении — отказ.

---

### User Story 4 - Уведомления админу (Priority: P3)

При новой регистрации бот отправляет уведомление в служебный Telegram-чат (корпоративная группа HR/IT) или лично всем админам — кто присоединился, по какому invite.

**Why this priority**: Удобно для команды, не обязательно для MVP, но сильно упрощает контроль.

**Independent Test**: Настроить `ADMIN_NOTIFY_CHAT_ID` → новый пользователь регистрируется → в чат приходит сообщение.

**Acceptance Scenarios**:

1. **Given** настроен `ADMIN_NOTIFY_CHAT_ID`, **When** новый сотрудник активирует invite, **Then** в чат уходит: `@username` (или имя), ID, invite-метка, время.
2. **Given** чат не настроен, **When** регистрация, **Then** уведомления админам в личку (fallback на `ADMIN_USER_IDS`).

---

### Edge Cases

- Пользователь уже в whitelist (env или DB) переходит по invite → бот сообщает «вы уже имеете доступ», дубликат не создаётся.
- Пользователь заблокирован переходит по invite → отказ, invite не «сжигается».
- Ссылка скопирована без параметра `start` → обычный `/start` без доступа + подсказка запросить invite у админа.
- Админ отзывает invite, по которому уже зарегистрировались N человек → зарегистрированные остаются, новые по этой ссылке — нет.
- Несколько админов → все с `ADMIN_USER_IDS` имеют одинаковые права на invite/users.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST позволять админу создавать invite-токены через команду бота (`/invite create`).
- **FR-002**: Система MUST генерировать deep link `https://t.me/{bot_username}?start=invite_{token}`.
- **FR-003**: Система MUST поддерживать опциональный пароль на invite (`/invite create --password` или интерактивный ввод).
- **FR-004**: Система MUST хранить пароли invite только в виде хеша (bcrypt или argon2).
- **FR-005**: Система MUST добавлять зарегистрированных пользователей в динамический whitelist (SQLite), не требуя правки `.env`.
- **FR-006**: Система MUST сохранять обратную совместимость с `ALLOWED_USER_IDS` из env (статический + динамический whitelist объединяются).
- **FR-007**: Система MUST позволять админу просматривать список пользователей (`/users`) и детали (`/user`).
- **FR-008**: Система MUST позволять админу блокировать/разблокировать пользователя (`/user block`, `/user unblock`).
- **FR-009**: Система MUST позволять админу отзывать invite (`/invite revoke <code>`).
- **FR-010**: Система MUST логировать факт регистрации (user_id, invite_id, timestamp) в SQLite.
- **FR-011**: Система SHOULD отправлять уведомление админам/в служебный чат при новой регистрации.
- **FR-012**: Invite MUST иметь настраиваемые параметры: срок действия (default 7 дней), max_uses (default 1, 0 = безлимит).

### Key Entities

- **Invite**: токен, пароль (hash), создатель, max_uses, use_count, expires_at, status (active/revoked/expired), label (опционально, напр. «Отдел продаж»).
- **RegisteredUser**: telegram_user_id, username, display_name, registered_at, invite_id, is_active, blocked_at.
- **InviteRedemption**: invite_id, user_id, redeemed_at.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Админ создаёт invite и регистрирует нового пользователя за ≤2 минуты без доступа к серверу.
- **SC-002**: 100% невалидных/просроченных invite получают понятный отказ.
- **SC-003**: `/users` отображает всех зарегистрированных через invite + env-whitelist пользователей.
- **SC-004**: Блокировка пользователя вступает в силу на следующем сообщении (≤1 сек задержки).
- **SC-005**: Пароль invite не хранится и не передаётся в логах в открытом виде.

## Assumptions

- Админ(ы) уже заданы в `ADMIN_USER_IDS` (bootstrap — как сейчас).
- Отдельная веб-админка не нужна в v2.0; всё через команды Telegram-бота.
- Целевой масштаб: до 50 сотрудников, до 20 активных invite одновременно.
- Username бота известен при деплое (`BOT_USERNAME` в env или получение через `getMe`).
- Корпоративный «служебный чат» — обычная Telegram-группа, куда добавлен бот с правом писать.

## Out of Scope (v2.0)

- Веб-панель администратора
- SSO / корпоративная почта для верификации
- Автоматическая синхронизация с HR-системой
- Роли кроме admin / user
