# Feature Specification: Company Telegram Knowledge Bot

**Feature Branch**: `001-company-telegram-bot`

**Created**: 2026-06-26

**Status**: Draft

**Input**: User description: "Свой Telegram-бот с базой знаний компании (RAG) и LLM API — сотрудники задают вопросы и получают ответы по документам компании."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Задать вопрос и получить ответ (Priority: P1)

Сотрудник компании пишет боту в Telegram (личный чат или корпоративная группа) вопрос на естественном языке. Бот ищет релевантные фрагменты в базе знаний компании и формирует ответ с указанием источника (название документа).

**Why this priority**: Это основная ценность продукта для заказчика.

**Independent Test**: Загрузить 3–5 тестовых документов, задать вопрос, ответ которого есть в документах — бот возвращает корректный ответ и ссылку на источник.

**Acceptance Scenarios**:

1. **Given** сотрудник в whitelist и в базе есть документ с ответом, **When** он отправляет вопрос боту, **Then** бот отвечает за ≤30 секунд с релевантным текстом и названием источника.
2. **Given** в базе нет информации по вопросу, **When** сотрудник задаёт вопрос, **Then** бот явно сообщает, что ответа в базе знаний нет, и не выдумывает факты.
3. **Given** сотрудник не в whitelist, **When** он пишет боту, **Then** бот отклоняет запрос с понятным сообщением об отсутствии доступа.

---

### User Story 2 - Ограничение использования (Priority: P2)

Система ограничивает количество вопросов на сотрудника в день, чтобы уложиться в бюджет API ($50–100/мес на команду).

**Why this priority**: Без лимитов бюджет заказчика быстро исчерпается.

**Independent Test**: Отправить N+1 вопросов от одного пользователя — N-й проходит, (N+1)-й получает сообщение о лимите.

**Acceptance Scenarios**:

1. **Given** сотрудник не исчерпал дневной лимит, **When** он задаёт вопрос, **Then** запрос обрабатывается.
2. **Given** сотрудник исчерпал дневной лимит (по умолчанию 20/день), **When** он задаёт следующий вопрос, **Then** бот сообщает о лимите и время сброса.

---

### User Story 3 - Обновление базы знаний (Priority: P3)

Администратор добавляет или обновляет документы в базе знаний (PDF, Markdown, TXT). Система переиндексирует документы для поиска.

**Why this priority**: База без обновлений быстро устаревает.

**Independent Test**: Добавить новый `.md` файл в папку knowledge, запустить reindex, задать вопрос по новому содержимому — бот отвечает корректно.

**Acceptance Scenarios**:

1. **Given** админ кладёт новый документ в `knowledge/`, **When** запускается reindex (CLI или команда `/reindex` для админа), **Then** содержимое доступно для поиска в течение 5 минут.
2. **Given** документ удалён из `knowledge/`, **When** выполнен reindex, **Then** его содержимое больше не используется в ответах.

---

### Edge Cases

- Что если документ на русском, а вопрос на английском? → Бот отвечает на языке вопроса, если модель поддерживает.
- Что если PDF повреждён или пустой? → Reindex логирует ошибку, документ пропускается, админ получает уведомление.
- Что если LLM API недоступен? → Бот отвечает «Сервис временно недоступен, попробуйте позже».
- Что если сообщение слишком длинное? → Бот просит сократить вопрос (лимит ~2000 символов).
- Что если несколько сотрудников пишут одновременно? → Запросы обрабатываются параллельно без блокировки друг друга.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать текстовые сообщения через Telegram Bot API.
- **FR-002**: Система MUST проверять Telegram user ID отправителя по whitelist перед обработкой.
- **FR-003**: Система MUST выполнять семантический поиск по индексированным документам компании (RAG).
- **FR-004**: Система MUST генерировать ответ через внешний LLM API (OpenRouter или совместимый).
- **FR-005**: Система MUST указывать источник ответа (название файла/документа).
- **FR-006**: Система MUST отказываться отвечать, если релевантных фрагментов не найдено (anti-hallucination prompt).
- **FR-007**: Система MUST ограничивать количество запросов на пользователя в сутки (настраиваемый лимит, default: 20).
- **FR-008**: Система MUST поддерживать форматы документов: `.md`, `.txt`, `.pdf` для v1.
- **FR-009**: Система MUST предоставлять CLI-команду `reindex` для переиндексации базы знаний.
- **FR-010**: Система MUST логировать запросы (user_id, timestamp, question length, tokens used) без сохранения полного текста вопроса (опционально — configurable).

### Key Entities

- **Employee**: Telegram user ID, display name, daily query count, last query timestamp, access status (allowed/denied).
- **Document**: File path, title, format, chunk count, indexed_at, status (active/error).
- **DocumentChunk**: Parent document, text content, embedding vector, chunk index.
- **QueryLog**: Employee reference, timestamp, tokens_used, sources_cited, status (success/rate_limited/error/no_answer).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 90% тестовых вопросов с известным ответом в базе получают корректный ответ (manual QA на 20 вопросах).
- **SC-002**: Среднее время ответа ≤30 секунд при базе до 100 документов.
- **SC-003**: Неавторизованные пользователи получают отказ в 100% случаев.
- **SC-004**: При исчерпании дневного лимита пользователь получает понятное сообщение в 100% случаев.
- **SC-005**: Система работает 24/7 на managed-хостинге с uptime ≥99% (цель для production).

## Assumptions

- Целевая аудитория: 10–30 сотрудников компании.
- Telegram — единственный канал в v1.
- Документы предоставляет заказчик; начальный объём до ~100 файлов.
- Данные можно отправлять в облачный LLM API (OpenRouter).
- Администратор — один человек с доступом к серверу/репозиторию.
- Языки: русский (основной), английский (поддержка модели).
- Бюджет API+хостинг: $50–100/мес.
