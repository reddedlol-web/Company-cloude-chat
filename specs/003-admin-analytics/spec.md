# Feature Specification: Админская аналитика и сводки по использованию бота

**Feature Branch**: `003-admin-analytics`

**Created**: 2026-06-29

**Status**: Draft

**Depends on**: `001-company-telegram-bot` (RAG, query_logs, rate limits), `002-admin-onboarding` (список пользователей, админ-команды)

**Input**: Администратору нужна прозрачность: что спрашивают сотрудники, как отвечает бот, нормально ли это, не тратятся ли токены впустую. Периодическая «сжатая» сводка (раз в день или неделю) + возможность посмотреть статистику по запросу — без перечисления каждого сообщения.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Сводка за период (Priority: P1)

Администратор получает автоматическую сводку в Telegram (личка или служебный чат): сколько было вопросов, сколько токенов потрачено, топ-темы, проблемные случаи (нет ответа в базе, ошибки, подозрение на оффтоп), рекомендации.

**Why this priority**: Главная ценность для заказчика — контроль процесса без ручного чтения всех чатов.

**Independent Test**: Сгенерировать 20+ тестовых запросов разных типов → запустить `/report daily` → админ получает читаемую сводку ≤4096 символов.

**Acceptance Scenarios**:

1. **Given** за сутки было ≥5 запросов, **When** срабатывает ежедневная сводка (или админ вызывает `/report daily`), **Then** сообщение содержит: всего запросов, уникальных пользователей, сумму токенов, разбивку по статусам (`success`, `no_answer`, `error`, `rate_limited`), 3–7 сгруппированных тем вопросов (не дословно каждый вопрос).
2. **Given** за неделю мало активности (0–2 запроса), **When** еженедельная сводка, **Then** бот отправляет краткое «активность низкая» без вызова LLM-суммаризации.
3. **Given** админ настроил `ANALYTICS_REPORT_CHAT_ID`, **When** сводка готова, **Then** она уходит в этот чат; иначе — всем `ADMIN_USER_IDS`.

---

### User Story 2 - Статистика по запросу (Priority: P1)

Администратор в любой момент запрашивает цифры: `/stats` (сегодня), `/stats week`, `/stats month`.

**Why this priority**: Нужен быстрый ответ «всё ли норм» без ожидания расписания.

**Independent Test**: `/stats` после 10 запросов показывает корректные счётчики и топ-3 источника из базы знаний.

**Acceptance Scenarios**:

1. **Given** админ, **When** `/stats`, **Then** ответ за сегодня (UTC): запросы, пользователи, токены in/out, % ответов из базы vs «нет ответа».
2. **Given** админ, **When** `/stats week`, **Then** агрегат за 7 дней + сравнение с прошлой неделей (↑/↓ %).
3. **Given** не-админ, **When** `/stats`, **Then** отказ (как для других admin-команд).

---

### User Story 3 - Выявление «ненормального» использования (Priority: P2)

Система помечает аномалии: пользователь близок к лимиту, много вопросов без попадания в базу, повторяющиеся однотипные запросы, высокий расход токенов на одного человека.

**Why this priority**: Помогает админу вовремя остановить «слив» бюджета на бессмысленные вопросы.

**Independent Test**: Симулировать 15 `no_answer` от одного user_id → в сводке флаг «пользователь X: 15 вопросов без ответа в БЗ».

**Acceptance Scenarios**:

1. **Given** пользователь за день ≥80% запросов со статусом `no_answer`, **When** формируется сводка, **Then** в блоке «⚠️ Внимание» указан user_id/username и краткое описание.
2. **Given** пользователь исчерпал ≥90% дневного лимита, **When** `/stats` или сводка, **Then** отображается предупреждение.
3. **Given** запрос классифицирован как `off_topic` (эвристика + опционально LLM), **When** логируется, **Then** учитывается в аналитике отдельно от `no_answer`.

---

### User Story 4 - Детализация по пользователю (Priority: P2)

Админ смотрит активность конкретного сотрудника: `/userstats <telegram_id>` — запросы за период, токены, темы, последние N вопросов (сокращённо).

**Why this priority**: Расширяет `/user` из 002 аналитикой, а не только фактом регистрации.

**Independent Test**: `/userstats 123456` показывает корректную статистику для тестового пользователя.

**Acceptance Scenarios**:

1. **Given** админ и существующий user_id, **When** `/userstats <id>`, **Then** карточка: запросов сегодня/неделя, токены, топ источников, 5 последних вопросов (первые 80 символов).
2. **Given** user_id без активности, **When** `/userstats <id>`, **Then** «активности нет за выбранный период».

---

### User Story 5 - Мини-дашборд (HTML) (Priority: P3)

Опционально: лёгкая read-only HTML-страница со статистикой за 30 дней, доступная только по секретному токену в URL (без логина). Для админа, которому удобнее смотреть в браузере.

**Why this priority**: Улучшает UX, но не блокирует MVP — Telegram-сводки достаточно для v3.0.

**Independent Test**: Открыть `http://host:8080/admin/dashboard?token=...` → видны графики/таблицы агрегатов.

**Acceptance Scenarios**:

1. **Given** `ANALYTICS_DASHBOARD_ENABLED=true` и задан `ANALYTICS_DASHBOARD_TOKEN`, **When** GET с верным токеном, **Then** HTML с KPI и таблицей по дням.
2. **Given** неверный токен, **When** запрос, **Then** 401 без данных.

---

### Edge Cases

- Нет запросов за период → сводка «активности не было», без LLM-вызова.
- Слишком длинная сводка → разбивка на 2–3 Telegram-сообщения или обрезка с «полный отчёт: /report daily --full».
- LLM для суммаризации недоступен → fallback на чисто числовой отчёт без тематических инсайтов.
- Retention: вопросы старше N дней удаляются из `query_details`, агрегаты в `daily_stats` сохраняются.
- Приватность: полный текст вопроса хранится только если `ANALYTICS_STORE_QUESTIONS=true` (default: true для корпоративного бота с ≤50 пользователей).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST собирать агрегированную статистику по `query_logs` (и расширенным полям) за день/неделю/месяц.
- **FR-002**: Система MUST позволять админу запрашивать статистику: `/stats`, `/stats week`, `/stats month`.
- **FR-003**: Система MUST генерировать текстовую сводку за период: `/report daily`, `/report weekly`.
- **FR-004**: Система MUST отправлять автоматические сводки по расписанию (настраиваемо: daily/weekly, время UTC).
- **FR-005**: Сводка MUST быть сжатой: тематические кластеры вместо полного списка всех вопросов; не более 7 тем + блок аномалий.
- **FR-006**: Система MUST опционально использовать LLM для группировки тем и формулировки рекомендаций (отдельный лимит токенов на отчёт).
- **FR-007**: Система MUST хранить текст вопроса (или усечённый) в `query_details` при `ANALYTICS_STORE_QUESTIONS=true`.
- **FR-008**: Система MUST классифицировать запросы: `answered`, `no_answer`, `off_topic`, `error`, `rate_limited`, `unauthorized`.
- **FR-009**: Система MUST выявлять аномалии по порогам (настраиваемые defaults в env).
- **FR-010**: Система MUST предоставлять `/userstats <telegram_id>` для админа.
- **FR-011**: Система SHOULD предоставлять опциональный HTML-дашборд (P3).
- **FR-012**: Система MUST логировать факт генерации отчёта (period, tokens_used, delivery_status).
- **FR-013**: Система MUST поддерживать retention полных текстов вопросов (default 90 дней).

### Key Entities

- **QueryDetail**: расширение лога — question_text (truncated), category, topic_cluster_id (после batch).
- **DailyStats**: дата, total_queries, unique_users, tokens_in/out, by_status JSON, top_sources JSON.
- **AnalyticsReport**: period_type, period_start/end, generated_at, summary_text, anomalies JSON, llm_tokens_used.
- **AnomalyFlag**: user_id, type, severity, description, detected_at.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Админ получает ежедневную сводку без ручных действий (если включено расписание).
- **SC-002**: `/stats` отвечает за ≤2 с при ≤5000 записей в `query_logs`.
- **SC-003**: Сводка за день укладывается в ≤3 Telegram-сообщения при 100+ запросах.
- **SC-004**: ≥90% аномалий (no_answer spike, лимит) попадают в блок «Внимание» сводки.
- **SC-005**: Расход токенов на генерацию одной сводки ≤5000 output tokens (настраиваемый cap).

## Assumptions

- Масштаб: до 50 пользователей, до ~500 запросов/день в пике.
- Админ уже определён в `ADMIN_USER_IDS`; служебный чат — тот же паттерн, что в 002.
- Для тематической группировки допустим один LLM-вызов на сводку (дешёвая модель).
- Полный текст вопросов нужен админу для контроля; retention ограничивает риски.

## Out of Scope (v3.0)

- Полноценная BI-платформа (Metabase, Grafana)
- Экспорт в Excel/PDF
- Real-time websocket-дашборд
- Автоматическая блокировка пользователей по аномалиям (только уведомление админу)
